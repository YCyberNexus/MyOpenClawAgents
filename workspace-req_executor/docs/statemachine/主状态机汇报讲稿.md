# req_executor 状态机讲稿

req_executor 的状态机围绕 GitLab issue 标签运行。`todo`、`new`、`retry` 会触发 fresh attempt；`continue` 会触发续跑；执行中是 `doing`；分支推送成功后短暂进入 `done`。普通请求创建 MR 后进入稳定完成态 `pr`，等待人工处理。用户明确要求自动合并时，固定外层执行器先精确 GET，并对 GitLab 临时 merge-readiness 状态做有界只读复核，再以带提交 SHA 的唯一 PUT、精确 GET 确认匹配 MR 已合并，随后原子写入稳定完成态 `finish`；Phase 6 不延后首次标签写入，而是在提交 durable 终态和回调前独立有界复核相同 MR 身份、分支与 SHA。失败按侧区分为 `blocked-cc`、`failed-cc`、`timeout`、`blocked-dispatcher`、`failed-dispatcher`。

当前执行模型很简单：issue 内容就是 Claude Code 的任务提示。调度器负责准备 `.req_executor` 运行目录、生成 prompt、启动 subagent、接收结果、同步标签和 MR，并把入口解析并冻结的处理基准、`auto_merge` 与 `merge_target_branch` 一路传到当前 attempt。显式请求分支优先；请求未指定时按“Issue 版本化 marker/唯一严格声明 → 仓库默认分支”解析。合并目标优先取用户明确指定的目标，否则跟随最终处理基准。单凭合并结果 marker 或回调内容不能授权 `finish`；Phase 6 无法独立确认时也不能提交成功终态或成功回调。

如果任务需要额外账号、测试数据、环境说明或项目特定材料，应写在 issue 内容或仓库文件里，不再通过 req_executor 的触发字段传递。
